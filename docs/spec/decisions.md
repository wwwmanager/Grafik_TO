# Решения владельца по ТЗ (2026-11-23) — дополняют TZ.md, при конфликте приоритет здесь

D1 Глубина: исключать, если `Дата ТО` < 01.01.(целевой год − глубина).
D2 А4: от последнего ТО шаги +6 мес.; берутся даты, попавшие в целевой год. Просроченная дата → наименее
   загруженный месяц; следующая = она + 6 мес. (если в году).
D3 Визит всегда 1 день. Если длительность > рабочего дня — визит занимает весь день, флаг «перегруз» в Детализации.
D4 Переезд 60 мин только между визитами из РАЗНЫХ населённых пунктов; внутри одного — 0.
D5 Вариант Б, текст примечания: «Физические лица, имеющие не более 3 ед. техники, проходят ТО в приёмные дни
   ({дни}) по адресу инспекции: {адрес}.» Поле «Адрес инспекции» в настройках.
D6 Реальная выгрузка: 1-я строка «Выгрузка на ДД.ММ.ГГГГ», заголовки НЕ в первой строке (в образце — 4-я).
   Парсер ищет строку заголовков сканированием первых 30 строк (строка, где есть `Владелец` и `Дата ТО`).
   Полный список заголовков — `headers-sample.txt`. Колонка `Группа владельца` есть; `Группа` — другое (группа техники).
D7 `Дата след. ТО` есть в выгрузке: если значение валидно — это целевая дата (для А4 вторая = +6 мес.);
   иначе расчёт по TZ (Дата ТО + период). Источник даты пишется в Детализацию.
D8 Гео-группировка без внешних сервисов: из `Адрес владельца` извлекаются район (`... р-н`/`район`) и населённый
   пункт (маркеры г., с., п., пгт, д., х., ст-ца, аул, рп и полные слова). Ключ локации = район|пункт (нормализовано).
   Расстановка: при выборе дня (среди допустимых, не позже целевой даты, в пределах окна группировки назад)
   приоритет — день, где уже есть визит того же пункта, затем того же района, затем любой. Лист `Локации`
   не нужен; ключ локации выводится в Детализации, чтобы пользователь видел, как распознан адрес.
D9 GitHub: репозиторий `Grafik_TO` в авторизованном `gh` аккаунте (публичный — Pages бесплатно; данных в репо нет).
D10 CORS isdayoff.ru: агент проверяет с реального Pages-origin; при отказе — встроенный JSON + плашка в UI.

## Поправки после первой приёмки (2026-11-23)

D11 Порог физлиц — настройка «Порог физлиц, ед.» (по умолчанию 3) вместо жёсткого ≤3. Физлицо с числом
    единиц ≤ порога (считаются только единицы, прошедшие фильтры) — режим А: не в графике; режим Б: в примечание
    (текст D5 подставляет порог вместо «3»). Баг: на реальной выгрузке физлица с 3 ед. попали в график —
    найти причину (распознавание физлица / подсчёт / ключ владельца), тесты на 2, 3, 4 ед.
D12 `Без ТО` = «*» означает: ТО ПРОСРОЧЕНО, техника НУЖДАЕТСЯ в ТО и всегда идёт в график (не исключение).
    Пусто — обычная техника. Глубина (D1) распространяется и на «*». Прочие причины исключения (снятие, угон,
    сдан ГРЗ, вывезена) в силе и сильнее «*».
D13 «*» при пустой/некорректной `Дата ТО`: считать последнее ТО старше 5 лет. В график — только если глубина
    ≥ 5; иначе исключить с причиной «нет даты ТО, глубина < 5 лет».
D14 Зимние месяцы — для просроченной техники и «*» (нет жёсткой даты): настройки «Зимние месяцы»
    (по умолчанию дек, янв, фев) и «Загрузка зимних месяцев, %» (0–100, по умолчанию 30). Выбор наименее
    загруженного месяца взвешивает ёмкость зимнего месяца этим процентом (0 — зиму не загружать; 100 — как
    обычные). Техника с обычной целевой датой остаётся на своей дате.
D15 Малые владельцы (GRAFIK-14) группируются по дате последнего ТО.
D16 Дата ТО текущего года ≥ даты выгрузки — техника в срок; дата переносится на целевой год (GRAFIK-18).
D17 Отпусков инспектора может быть несколько. «Машин в час» 1–100, по умолчанию 12 (GRAFIK-19).
D18 Время осмотра округляется до 30 мин. Переезд = (число разных НП визитов дня − 1) × «Переезд, мин» (GRAFIK-26).
D19 Статусов два, с точностью до дня (GRAFIK-29, заменяет GRAFIK-27): «Просрочен (ДД.ММ.ГГГГ)» — дата <
    даты выгрузки; иначе «По графику (ДД.ММ.ГГГГ)». «*» без даты — «Просрочен (дата неизвестна)».
D20 Физлица в графике (GRAFIK-32..35). Галочка «Включать физлиц в график» (по умолчанию выкл.; выкл. —
    поведение D5). Кого группировать: только физлиц до порога D11 (по умолчанию) или всех физлиц.
    Точка = населённый пункт (самый мелкий из адреса; родитель — район, иначе город) × месяц целевой даты.
    В каждом месяце близлежащие НП объединяются в маршрут на один день (несколько НП попутно): старт от
    «НП инспекции», радиус «Радиус маршрута, км» (40), переезд = расстояние по прямой × 1,3 / «Средняя
    скорость» (50 км/ч), порядок — ближайший следующий; день заполняется по ёмкости, крупные НП — на
    несколько дней. Маршрут ≥ «Мин. единиц техники для выезда» (по умолч. 5) — выездной день; меньше —
    ТО на площадке в «Дни площадки» (по умолч. = приёмные дни). Площадка: «у инспекции» (адрес инспекции) или «своя площадка» с адресом.
    Ручные объединения/разделения хранятся в браузере до загрузки другой выгрузки, только названия НП.
    Excel: строки «ТО физлиц: п. Тайнак, п. Тундуш (Златоуст) — 9 чел., 12 ед.» и «ТО физлиц на площадке:
    <адрес> — N чел., M ед.»; ФИО — в «Детализации».
D21 Справочник НП — только OpenStreetMap (ODbL, указание источника), офлайн-JSON в репозитории. ГАР не
    используется: в нём нет координат. Координаты НП используются для маршрутов D20.
D23 Все регионы РФ (GRAFIK-36). Справочники НП собираются из OSM заранее, по файлу на регион:
    `public/data/settlements/<код>.json` + список `public/data/regions.json` ({code, iso, name, file, count,
    bytes}). В настройках «Регион инспекции» (+ соседние, мультивыбор); по умолчанию — регион большинства
    адресов выгрузки, иначе ручной выбор. Браузер грузит только выбранные. Обновление — раз в квартал
    командой `npm run data:settlements` (D8 в силе: в работе внешних сервисов нет). Допущение: формат
    выгрузки в других регионах тот же; при отличии нужен образец.
D22 «Окно группировки» объединяет в один визит технику ОДНОГО владельца; предел 1–365 дней (GRAFIK-31).

D24 Одноимённые НП в одном районе НЕ удаляются из справочника. Признак дубля — совпадение OSM-объекта
    (id или имя+район+координаты до 3 знаков), это уже чистит сборщик (GRAFIK-39). Совпадение имени при
    разных координатах считается разными НП (село + станция/посёлок; 17 групп в Челябинской обл., разлёт
    1.4–19 км). Разбор в GRAFIK-33: если кандидатов с тем же именем несколько, выбирать по типу из адреса
    (город/село/деревня/посёлок), иначе ближайший к базовому НП и помечать ambiguous для ручного выбора.
    Причина: удаление реальных НП ломает разбор адресов; цена лишней записи — ноль.

D25 Внутренний идентификатор региона (dataId) ≠ официальный код ФНС/ИНН (regionCode). Раньше одно поле `code`
    выполняло обе роли: имя файла справочника НП (`settlements/<code>.json`), ключ в localStorage и отображаемый
    код в UI. Теперь разделены:
    - `dataId` (1..89) — последовательный внутренний ключ, используется для: имени файла справочника НП
      (не меняются, 81 файл, 14.66 МБ), ключа в localStorage (`inspectionRegion`, `neighboringRegions`),
      индекса массива REGIONS_TABLE. dataId НЕ меняется между ребилдами.
    - `regionCode` (1–96) — официальный 2-значный код ФНС/ИНН (префикс ОКТМО), используется ТОЛЬКО для
      отображения в UI: `Челябинская область (74)`, `Тюменская область (72)`, `Чувашская Республика (21)` и т.д.
    Таблица соответствия (89 строк) — единственный источник: `scripts/build-settlements.mjs` →
    `src/modules/regions-table.js` (регенерируется скриптом `generate-regions-table.mjs`, ручное редактирование
    запрещено). Примеры расхождений (было → стало): Челябинская 72→74, Тюменская 66→72, Чувашия 74→21,
    Ярославская 77→76, ХМАО 71→86, ЯНАО 76→89, Удмуртия 67→18, Мордовия 82→13, Крым 80→91, Севастополь 81→92
    (ГИБДД использует 82 для Крыма — зафиксировано, не подбирается автоматически).
    Новые территории (Донецкая, Луганская, Запорожская, Херсонская) — официальных ФНС кодов нет; им присвоены
    уникальные regionCode 93–96 (dataId 86–89), задокументировано здесь.
    UI: все 89 регионов всегда доступны для выбора (нет `disabled`). Регионы без гео-справочника показывают
    инлайн-подсказку «гео-справочник не загружен — используется текстовая группировка по адресам».
    Соседние регионы — вертикальный список в прокручиваемом блоке (max-height 180px) с компактным поиском.
    Настройки сохраняют dataId → никакой миграции localStorage не требуется, потерь данных нет.
