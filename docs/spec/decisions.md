# Решения владельца по ТЗ (2026-11-23) — дополняют TZ.md, при конфликте приоритет здесь

D1 Глубина: исключать, если `Дата ТО` < 01.01.(целевой год − глубина).
D2 А4: от последнего ТО шаги +6 мес.; берутся даты, попавшие в целевой год. Просроченная дата → наименее
   загруженный месяц; следующая = она + 6 мес. (если в году).
D3 Визит всегда 1 день. Если длительность > рабочего дня — визит занимает весь день, флаг «перегруз» в Детализации.
D4 Переезд 60 мин только между визитами из РАЗНЫХ населённых пунктов; внутри одного — 0.
D5 Вариант Б, текст примечания: «Физические лица, имеющие не более 3 ед. техники, проходят ТО в приёмные дни
   ({дни}) по адресу инспекции: {адрес}.» Поле «Адрес инспекции» в настройках.
D6 Реальная выгрузка: 1-я строка «Выгрузка на ДД.ММ.ГГГГ», заголовки НЕ в первой строке (в образце — 4-я).
   Парсер ищет строку заголовков сканированием первых 30 строк (строка, где есть `Владелец` и `Дата ТО`).
   Полный список заголовков — `headers-sample.txt`. Колонка `Группа владельца` есть; `Группа` — другое (группа техники).
D7 `Дата след. ТО` есть в выгрузке: если значение валидно — это целевая дата (для А4 вторая = +6 мес.);
   иначе расчёт по TZ (Дата ТО + период). Источник даты пишется в Детализацию.
D8 Гео-группировка без внешних сервисов: из `Адрес владельца` извлекаются район (`... р-н`/`район`) и населённый
   пункт (маркеры г., с., п., пгт, д., х., ст-ца, аул, рп и полные слова). Ключ локации = район|пункт (нормализовано).
   Расстановка: при выборе дня (среди допустимых, не позже целевой даты, в пределах окна группировки назад)
   приоритет — день, где уже есть визит того же пункта, затем того же района, затем любой. Лист `Локации`
   не нужен; ключ локации выводится в Детализации, чтобы пользователь видел, как распознан адрес.
D9 GitHub: репозиторий `Grafik_TO` в авторизованном `gh` аккаунте (публичный — Pages бесплатно; данных в репо нет).
D10 CORS isdayoff.ru: агент проверяет с реального Pages-origin; при отказе — встроенный JSON + плашка в UI.

## Поправки после первой приёмки (2026-11-23)

D11 Порог физлиц — настройка «Порог физлиц, ед.» (по умолчанию 3) вместо жёсткого ≤3. Физлицо с числом
    единиц ≤ порога (считаются только единицы, прошедшие фильтры) — режим А: не в графике; режим Б: в примечание
    (текст D5 подставляет порог вместо «3»). Баг: на реальной выгрузке физлица с 3 ед. попали в график —
    найти причину (распознавание физлица / подсчёт / ключ владельца), тесты на 2, 3, 4 ед.
D12 `Без ТО` = «*» означает: ТО ПРОСРОЧЕНО, техника НУЖДАЕТСЯ в ТО и всегда идёт в график (не исключение).
    Пусто — обычная техника. Глубина (D1) распространяется и на «*». Прочие причины исключения (снятие, угон,
    сдан ГРЗ, вывезена) в силе и сильнее «*».
D13 «*» при пустой/некорректной `Дата ТО`: считать последнее ТО старше 5 лет. В график — только если глубина
    ≥ 5; иначе исключить с причиной «нет даты ТО, глубина < 5 лет».
D14 Зимние месяцы — для просроченной техники и «*» (нет жёсткой даты): настройки «Зимние месяцы»
    (по умолчанию дек, янв, фев) и «Загрузка зимних месяцев, %» (0–100, по умолчанию 30). Выбор наименее
    загруженного месяца взвешивает ёмкость зимнего месяца этим процентом (0 — зиму не загружать; 100 — как
    обычные). Техника с обычной целевой датой остаётся на своей дате.
D15 Малые владельцы (GRAFIK-14) группируются по дате последнего ТО.
D16 Дата ТО текущего года ≥ даты выгрузки — техника в срок; дата переносится на целевой год (GRAFIK-18).
D17 Отпусков инспектора может быть несколько. «Машин в час» 1–100, по умолчанию 12 (GRAFIK-19).
D18 Время осмотра округляется до 30 мин. Переезд = (число разных НП визитов дня − 1) × «Переезд, мин» (GRAFIK-26).
D19 Статусов два, с точностью до дня (GRAFIK-29, заменяет GRAFIK-27): «Просрочен (ДД.ММ.ГГГГ)» — дата <
    даты выгрузки; иначе «По графику (ДД.ММ.ГГГГ)». «*» без даты — «Просрочен (дата неизвестна)».
D20 Физлица в графике (GRAFIK-32..35). Галочка «Включать физлиц в график» (по умолчанию выкл.; выкл. —
    поведение D5). Кого группировать: только физлиц до порога D11 (по умолчанию) или всех физлиц.
    Точка = населённый пункт (самый мелкий из адреса; родитель — район, иначе город) × месяц целевой даты.
    В каждом месяце близлежащие НП объединяются в маршрут на один день (несколько НП попутно): старт от
    «НП инспекции», радиус «Радиус маршрута, км» (40), переезд = расстояние по прямой × 1,3 / «Средняя
    скорость» (50 км/ч), порядок — ближайший следующий; день заполняется по ёмкости, крупные НП — на
    несколько дней. Маршрут ≥ «Мин. единиц техники для выезда» (по умолч. 5) — выездной день; меньше —
    ТО на площадке в «Дни площадки» (по умолч. = приёмные дни). Площадка: «у инспекции» (адрес инспекции) или «своя площадка» с адресом.
    Ручные объединения/разделения хранятся в браузере до загрузки другой выгрузки, только названия НП.
    Excel: строки «ТО физлиц: п. Тайнак, п. Тундуш (Златоуст) — 9 чел., 12 ед.» и «ТО физлиц на площадке:
    <адрес> — N чел., M ед.»; ФИО — в «Детализации».
D21 Справочник НП — только OpenStreetMap (ODbL, указание источника), офлайн-JSON в репозитории. ГАР не
    используется: в нём нет координат. Координаты НП используются для маршрутов D20.
D23 Все регионы РФ (GRAFIK-36). Справочники НП собираются из OSM заранее, по файлу на регион:
    `public/data/settlements/<код>.json` + список `public/data/regions.json` ({code, iso, name, file, count,
    bytes}). В настройках «Регион инспекции» (+ соседние, мультивыбор); по умолчанию — регион большинства
    адресов выгрузки, иначе ручной выбор. Браузер грузит только выбранные. Обновление — раз в квартал
    командой `npm run data:settlements` (D8 в силе: в работе внешних сервисов нет). Допущение: формат
    выгрузки в других регионах тот же; при отличии нужен образец.
D22 «Окно группировки» объединяет в один визит технику ОДНОГО владельца; предел 1–365 дней (GRAFIK-31).

D24 Одноимённые НП в одном районе НЕ удаляются из справочника. Признак дубля — совпадение OSM-объекта
    (id или имя+район+координаты до 3 знаков), это уже чистит сборщик (GRAFIK-39). Совпадение имени при
    разных координатах считается разными НП (село + станция/посёлок; 17 групп в Челябинской обл., разлёт
    1.4–19 км). Разбор в GRAFIK-33: если кандидатов с тем же именем несколько, выбирать по типу из адреса
    (город/село/деревня/посёлок), иначе ближайший к базовому НП и помечать ambiguous для ручного выбора.
    Причина: удаление реальных НП ломает разбор адресов; цена лишней записи — ноль.

D25 Внутренний идентификатор региона (dataId) ≠ коды субъекта: ФНС/ИНН (fnsCode) и ГИБДД (gibddCode).
    Раньше одно поле `code` выполняло все роли: имя файла справочника НП (`settlements/<code>.json`),
    ключ в localStorage и отображаемый код в UI. Теперь разделены:
    - `dataId` — исходные значения кодов, ставшие именами файлов справочников НП (`1..88`, `95`;
      не последовательный, с пропусками), используется для: имени файла справочника НП
      (не меняются, 81 файл, 14.66 МБ), ключа в localStorage (`inspectionRegion`, `neighboringRegions`),
      индекса массива REGIONS_TABLE. dataId НЕ меняется между ребилдами.
    - `fnsCode` (1–96) — официальный 2-значный код ФНС/ИНН (префикс ОКТМО/ССРФ). Хранится для
      налоговой/адресной логики и как справочная пара; в UI НЕ отображается (с GRAFIK-49).
    - `gibddCode` — 2-значный код региона на государственных регистрационных знаках (приказ МВД России
      от 05.10.2017 № 766, приложение № 1). Именно он отображается и сортируется в UI (GRAFIK-49);
      подробности и таблица расхождений — D32.
    Таблица соответствия (89 строк) — единственный источник: `scripts/build-settlements.mjs` →
    `src/modules/regions-table.js` (регенерируется скриптом `generate-regions-table.mjs`, ручное редактирование
    запрещено). Исторические примеры миграции dataId → fnsCode (не отображение): Челябинская 72→74,
    Тюменская 66→72, Чувашия 74→21, Ярославская 77→76, ХМАО 71→86, ЯНАО 76→89, Удмуртия 67→18,
    Мордовия 82→13, Крым 80→91, Севастополь 81→92.
    Новые территории (Донецкая, Луганская, Запорожская, Херсонская) — ФНС-кода нет: `fnsCode: null`
    (не выдумываем коды), dataId 85–88 сохранены; при этом проверяемый код ГИБДД у них есть (80/81/85/84,
    см. D32), поэтому UI показывает `NN — Название`. Тесты исключают null из проверок уникальности
    каждого поля отдельно.
    UI: все 89 регионов всегда доступны для выбора (нет `disabled`). Регионы без гео-справочника показывают
    инлайн-подсказку «гео-справочник не загружен — используется текстовая группировка по адресам».
    Соседние регионы — вертикальный список в прокручиваемом блоке (max-height 180px) с компактным поиском.
    Настройки сохраняют dataId → никакой миграции localStorage не требуется, потерь данных нет.

D27 Защита от устаревшего кэша (GRAFIK-46): после деплоя GitHub Pages может отдать старый index.html,
    который ссылается на удалённые хешированные чанки -> 404 -> dynamic import отклонён -> UI навсегда
    в состоянии загрузки, единственный след — ошибка в консоли. Три уровня защиты:
    1) public/cache-guard.js — стабильный (не хешируемый) classic-скрипт, подключён в <head> index.html
       до module-entry. Ловит в capture-фазе error у <script type=module>/<link rel=stylesheet> и
       unhandledrejection про dynamic import; при первом сбое за сессию (sessionStorage
       grafik:preload-reloaded) делает один reload с ?v=<timestamp>, при повторе показывает баннер
       «Загружена устаревшая версия приложения — обновите страницу (Ctrl+F5)» (role=alert).
    2) src/modules/resilience.js — installPreloadGuard() слушает vite:preloadError (preventDefault),
       тот же ключ и баннер; loadModule() оборачивает каждый dynamic import (parser, exporter,
       physical, address, physicalTab) и при отклонении рендерит inline-ошибку с кнопкой «Повторить»
       (ошибка помечается guarded, чтобы вызывающий код не затёр её общим сообщением). Ни один путь
       не оставляет статус в вечной загрузке: сбой маршрутов физлиц показывает базовый график + retry,
       сбой справочника регионов/НП — retry в #messages, экспорт/разбор файла — retry соответствующего
       действия.
    3) scripts/check-deploy.mjs — read-only проверка живого сайта: fetch index.html, HEAD каждого
       assets/* из него, проверка что все ссылки dist/index.html существуют на диске; exit 1 при
       любом не-200/отсутствии файла, WARN при расхождении живого HTML с локальной сборкой.
    Перезагрузка не более одной на вкладку-сессию; при недоступном sessionStorage reload не делается
    (только баннер), чтобы не получить цикл. Логика покрыта тестами на фейковом DOM (node-окружение).

D28 Производительность маршрутов физлиц (GRAFIK-47): замер на реальном справочнике Челябинской
    (public/data/settlements/74.json, 1267 записей) и синтетическом экспорте из 150 адресов:
    resolve=12583 ms, group=0.3 ms, stops=0.5 ms, schedule=24.9 ms, итого 12608.6 ms — виноват
    resolveSettlement, который на КАЖДЫЙ адрес пересобирал нормализованный lookup (150 x 1267 x 2
    normalizeName). После: resolve=107.6 ms, stops=99.4 ms, schedule=105.3 ms, итого 312.5 ms.
    Решения:
    1) address.js: createSettlementIndex() строит один раз пары name|municipality, byName и
       byMunicipality с предвычисленной нормализацией; getSettlementIndex() кэширует индекс в WeakMap
       по массиву поселений; resolveSettlement(parsed, settlements|index) принимает и индекс.
       Порядок кандидатов сохранён (порядок пар вставки), fuzzy-скан идёт по index.pairs — поведение
       прежнее (тесты address.test.js и golden GRAFIK-35 зелёные).
    2) physical.js: selectRegionDataIds() грузит только регион экспорта/настройки (не все 89 файлов
       ~14.7 MB); запросы радиуса — через uniform grid (createRadiusGrid/queryRadiusGrid) с
       консервативным боксом и точной haversine-фильтрацией, кандидаты сортируются по исходному
       индексу, поэтому маршруты и tie-break идентичны полному скану (эквивалентность проверяется
       тестом против эталонного скана в tests/route-perf.test.js); расстояния от базы считаются один
       раз за месяц.
    3) Жёсткий дедлайн 15 с: createBuildRuntime/PhysicalBuildTimeoutError (code
       PHYSICAL_BUILD_TIMEOUT, сообщение с «Повторить»), withDeadline() для fetch-загрузки
       справочников, проверки по записям/маршрутам/месяцам, onProgress (phase, processed, total,
       elapsedMs) с троттлингом 200 ms и yield в event loop раз в 50 ms; ui.analyze показывает
       «поселения X/Y» / «месяцы X/12» и при таймауте — retry-сообщение.
    4) Данные справочников не менялись; 17 пар name|municipality в 74.json имеют разные координаты
       (village vs hamlet) — это реальные данные OSM, уникальность проверяется полным ключом.

D29 Загрузчик справочников НП (GRAFIK-43): loadSettlementsWithStatus(dataIds) возвращает
    { settlements, failed: [{ dataId, reason }] }; loadSettlements остаётся массивом для старых
    вызовов (ничего не бросает).
    - один in-flight promise на dataId: параллельные вызовы ждут тот же запрос, повторного fetch нет;
    - LRU на 6 регионов: Map в порядке вставки, попадание обновляет порядок (delete+set), при
      переполнении удаляется самый старый ключ и его данные; вытесненный регион при следующем
      выборе загружается заново;
    - ошибки (404/сеть) не кэшируются (поздний повторный выбор повторит загрузку), не бросаются,
      пишутся в console.warn; UI показывает подсказку «Гео-справочник для региона не загружен —
      используется текстовая группировка по адресам» (элемент #region-no-data-hint), текстовая
      группировка продолжает работать;
    - соседние регионы грузятся только при отметке чекбокса, снятие галочки кэш не чистит;
    - loadSelectedRegionSettlements('') не делает ни одного fetch: до выбора региона запросов 0.

D30 Базовый населённый пункт (GRAFIK-44): база маршрутов выводится из фактического экспорта, а не
    «первый в регионе». Чистая функция pickBaseSettlement(resolved, regionDataId, { manualSettlement,
    regionSettlements, total }) в address.js:
    - учитываются только успешно разрешённые адреса (exact/fuzzy) выбранного региона инспекции; адреса,
      разрешённые в соседнем регионе (другой dataId), отбрасываются;
    - агрегация по ключу name|municipality; победитель — мода по числу адресов; tie-break:
      1) больше адресов; 2) ближе к географическому центроиду разрешённых адресов региона (центроид
      группы — среднее координат группы, расстояние haversine); 3) имя (localeCompare ru);
    - ручной выбор побеждает, пока НП есть в справочнике региона (name+municipality); после реимпорта
      сохранённое значение восстанавливается, если НП существует, иначе игнорируется;
    - если ничего не разрешилось — прежнее поведение: первый НП региона (source='fallback'), и это
      явно написано в подписи;

D31 Отчёт о нераспознанных адресах (GRAFIK-45): после резолва и ДО построения графика в блоке
    «Физлица» показывается информационная сводка «Распознано N из M адресов · не разобрано K»
    (#unresolved-report) и раскрываемый список неразобранных строк: 1-based номер в порядке импорта +
    сырой адрес одной строкой (CSS ellipsis), кнопка «Скопировать неразобранные» кладёт в буфер
    строки «<номер>: <адрес>» только для неразобранных. Если M > 0 и N = 0 — предупреждающий баннер
    (неверный регион инспекции или нет гео-справочника), текстовая группировка продолжает работать.
    Отчёт ничего не блокирует и не меняет маршрутизацию/расписание; строится из in-memory данных
    импорта: не пишется в localStorage, не попадает в Excel, не логируется.

D32 Прокрутка панели настроек и короткие метки регионов (GRAFIK-48): регрессия GRAFIK-42 —

D32.1 Отображаемый код региона — ГИБДД, не ФНС (GRAFIK-49). Причина: владелец сверяет субъекты
    по коду на госномерах; для нескольких субъектов он расходится с кодом ФНС/ИНН (ОКТМО).
    Оба числа сохранены в таблице: `gibddCode` — отображается и сортируется, `fnsCode` — остаётся
    для налоговой/адресной логики и как справочная пара; данные не удалены. Источник кодов ГИБДД:
    приказ МВД России от 05.10.2017 № 766 «О государственных регистрационных знаках транспортных
    средств», приложение № 1 «Перечень цифровых кодов регионов…» (ред. от 09.12.2025); сверено по
    двум независимым справочникам — pdd.ru/region-codes и kakras.ru/doc/kody-regionov (оба
    ссылаются на приказ № 766; kakras дополнительно приводит официальную публикацию приказа
    МВД № 942 от 23.12.2025). Таблица расхождений (fnsCode -> gibddCode):
      Чеченская Республика 20 -> 95; Республика Крым 91 -> 82; Севастополь 92 -> 92 (совпадает);
      Донецкая Народная Республика null -> 80; Луганская Народная Республика null -> 81;
      Запорожская область null -> 85; Херсонская область null -> 84.
    Коды 80/81/84/85 ранее принадлежали упразднённым автономным округам и переназначены новым
    субъектам (2014/2022); «выдуманные» 93–96 не используются ни в одном поле. Если для субъекта
    проверяемого кода ГИБДД нет — `gibddCode: null`, UI показывает «— — Название» (сейчас таких нет).
    Регрессионные тесты: уникальность и 2-значность каждого непустого кода, фиксированные пары
    (включая 20->95 и 91->82), отсутствие 93/94/96, сортировка списка по gibddCode.
